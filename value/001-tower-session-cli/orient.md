# Claude セッションの中から Tower を操作する — 方向付け

feature-id: 001-tower-session-cli
日付: 2026-10-05

## 解こうとしている問題

Tower の Navigator は「セッションを眺めて選ぶ」ための道具で、セッションの中に
いる人(と、その中で動いている Claude)からは何も操作できない。その結果、
作業の実態と Navigator の表示が食い違っていく。

- セッションを使い回すと、Navigator の行の名前(最初のプロンプト)と今の
  作業内容が乖離し、どの行がどの作業か分からなくなる
- home ディレクトリのセッションで出たアイデアを、あるプロジェクトで続けたいとき、
  Navigator に戻って `n`/`N` で新セッションを作り、アイデアを手で打ち直している
- 新しいプロジェクトを始めるときは、ディレクトリ作成・`git init`・Tower への
  登録を別々の場所で手作業している

想定利用者:
- iwase 本人。tmux の中で 10 前後の Claude セッションを並行して回し、
  Navigator で切り替えている。多くの時間はセッションの中にいて、Navigator は
  一瞬開いて閉じる
- セッションの中で動いている Claude(スキル経由で `tower` を呼ぶ側)

今どうしているか:
- 名前: 変えられない。行の名前は最初のプロンプトのままで、内容が変わった
  セッションは「開いて中を見る」まで判別できない
- 移動: Navigator に戻り、`N` でディレクトリを選び、新セッションに要約を
  貼り直す。要約の作成はその場の手作業
- プロジェクト開始: シェルで `mkdir` と `git init`、その後 `tower add <dir>`
  または Navigator の `N`。登録の手順はどこにも書かれていない

## 作らない選択肢

### 案1: 何もしない
棄却理由: 名前の乖離は時間とともに悪化し、行数が増えるほど「どの行か」の
探索コストが増える。移動は毎回 1〜2 分の貼り直しで、アイデアの一部が落ちる
(本人の申告)。放置するとセッションの使い回しが増え、1 セッションの文脈が
肥大して compaction と品質低下を招く。

### 案2: 既存のもので代用する(tmux の rename-session、手作業の mkdir + tower add)
棄却理由: `tmux rename-session` は Tower のセッション名 `tower_<uuid>` を壊し、
Navigator がそのセッションを見失う。`tower add <dir>` は存在するが、Claude
セッションの中からは「自分がどのセッションか」「今の文脈をどう渡すか」の
部分が無く、手作業の貼り直しは残る。既存の道具は Navigator 側の操作を前提に
しているので、セッション内からの操作という文脈に噛み合わない。

### 案3: 問題の方を変える(セッションを使い回さない運用にする)
棄却理由: 「1 セッション 1 目的」を徹底すれば名前の乖離は起きないが、
Navigator を往復して `n` を押す摩擦が「使い回す」動機そのものであり、
運用ルールでは摩擦が消えない。摩擦を減らす道具が無いと運用は守られない。

## 価値仮説

```
VH-001: セッション名を作業の実態に合わせ直せる
  誰が    : セッションの中にいる iwase(または代理で動く Claude)
  いつ    : セッションの作業内容が最初の指示から離れたと気づいたとき
  今は    : 名前を変える手段が無く、行を開いて中身を見るまで判別できない
  これで  : `tower rename <name>` 一発で Navigator の行の名前が変わる
  その結果: Navigator を開いたとき、名前だけで目的の行を選べる
  外れ判定: 導入後 2 週間で rename が一度も使われない、または rename した
            セッションを選ぶのに依然として中身を開いて確認している
```

```
VH-002: 別プロジェクトで新セッションを始め、文脈を引き継げる
  誰が    : 別のディレクトリ(home 等)のセッションで作業中の iwase
  いつ    : その場で出たアイデアを特定プロジェクトで続けたくなったとき
  今は    : Navigator に戻って N で作成し、要約を手で貼り直している
  これで  : `tower open <project> --prompt-file <要約>` で新セッションが
            そのプロジェクトで始まり、要約が最初のプロンプトとして入り、
            Navigator の選択がそこに移る
  その結果: 貼り直しの手作業がゼロになり、要約の脱落が無くなる
  外れ判定: open で作ったセッションの最初のプロンプトが実際には使われず、
            利用者が改めて打ち直している(transcript で観測可能)
```

```
VH-003: プロジェクトを 1 コマンドで開始し、Navigator に現れる
  誰が    : 新しい repo を始める iwase
  いつ    : アイデアを独立したプロジェクトに切り出すとき
  今は    : mkdir・git init・tower add を別々に手作業
  これで  : `tower project new <name>` でディレクトリと git repo ができ、
            最初のセッションが始まり、Navigator にグループとして現れる
  その結果: プロジェクト開始が 1 コマンドで終わり、手順を覚えなくてよい
  外れ判定: project new で作った repo を、結局シェルで作り直している
            (git init の既定が合わない等)
```

## 価値の検証可能性

| 仮説 | 区分 | 受入での扱い |
|---|---|---|
| VH-001 | 機械判定可 | rename 後に Navigator の行文字列が新しい名前になる |
| VH-002 | 機械判定可 | open 後にセッションがそのディレクトリで動き、Navigator の `selected` が新セッションを指し、初回プロンプトが claude に渡っている |
| VH-003 | 機械判定可 | project new 後にディレクトリ・`.git`・セッション・metadata が揃っている |

「判断必要」に分類したものの分解を試みた記録:

- 「要約の質」(VH-002)は判断必要に見えるが、要約を書くのは呼び出し側の
  Claude であり、この機能の責任は「渡した文字列がそのまま最初のプロンプトに
  なること」。そこまでに分解すると機械判定可になる。要約の質はスキル
  (`skills/tower`)の文面で扱い、本機能の受入では見ない。

## 非スコープ

**今回作らないもの。** 構築契約の I6 としてそのまま渡る。

- GitHub 上のリポジトリ作成(`gh repo create`)。外部公開なので利用者が
  自分で行う。`project new` はローカル `git init` まで
- セッションが無い「空のプロジェクト」の台帳。Navigator のグループは
  セッションから導出される現行設計を変えない
- 元セッションを閉じる・休眠にする操作。`open` は新セッションを作って
  選択を移すだけで、元はそのまま残す
- Navigator 側の UI 追加(rename のキー等)。入口は `tower` CLI と、それを
  呼ぶスキルに限る
- CLAUDE.md や Issue 管理の初期化(`project new` の中では行わない)
- `tower project add <dir>`(E-009): 分節の第3段で `open <dir>` と結果が同じと
  判定(vf-articulate)。語彙が増えるだけで新しい意図を表さない

## 判断

- [x] 作る / [ ] 作らない

理由: 3 つの作らない選択肢はいずれも摩擦を残すか Tower を壊す。価値仮説は
3 つとも機械判定可で、外れ判定が書ける。既存の `session-add.sh` と
`metadata` の `session_name` に器があり、追加するのは CLI の入口と
文脈の受け渡しに絞れる。
