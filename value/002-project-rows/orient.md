# Navigator でプロジェクトを行として扱う — 方向付け

feature-id: 002-project-rows
日付: 2026-10-11

## 解こうとしている問題

Navigator の一覧は「セッションの集合」で、プロジェクトはセッションから導出される
見出しでしかない。利用者の頭の中では逆で、プロジェクトが先にあり、セッションは
その中の作業の単位。この食い違いが 2 つの形で表れる。

- プロジェクトのセッションを全部消すと、プロジェクト自体が一覧から消える。
  「いま作業中ではないが、戻ってくる場所」を Navigator が覚えていない
- 見出しにカーソルが止まらないので、「このプロジェクトで新しく始める」が
  見出しからできない。`n` はカーソルのあるセッションと無関係なディレクトリ
  (呼び出し元の cwd)を既定にし、`N` は picker で選び直させる

想定利用者:
- iwase。10 前後のプロジェクトを並行し、作業が一段落したプロジェクトの
  セッションは消す(文脈が古くなるため)。しかし数日後に同じプロジェクトへ戻る
- 一覧を「プロジェクト → セッション」の順で眺め、プロジェクトを起点に操作したい

今どうしているか:
- 消えたプロジェクトに戻るには `N` の picker(transcript の cwd 一覧)から探す。
  一覧は transcript の新しい順で、プロジェクトが多いと探す
- 「このプロジェクトで新規」は、同じプロジェクトのセッションにカーソルを
  合わせて `f`(fork here)を押す。セッションが 0 ならこの手が無い

## 作らない選択肢

### 案1: 何もしない
棄却理由: #67 で `tower open` / `project new` を入れたので、プロジェクト起点の
操作は増える。空になったプロジェクトが消える現状では、`project new` で作った
直後にセッションを閉じるとプロジェクトが「無かったこと」になり、#67 の価値が
半分削れる。

### 案2: 既存のもので代用する(消さずに休眠セッションを 1 つ残す)
棄却理由: 運用でしのげるが、「プロジェクトを残すためだけのセッション」は
一覧の雑音で、休眠(○)の意味も濁る。利用者はセッションを消したいのであって、
プロジェクトを消したいのではない。

### 案3: 問題の方を変える(プロジェクト一覧を別画面にする)
棄却理由: 画面が増え、j/k で辿る 1 本の一覧という Navigator の形を壊す。
見出しを行として扱えば、同じ一覧の中で済む。

## 価値仮説

```
VH-001: プロジェクトはセッションが無くても一覧に残る
  誰が    : 作業の切れ目でセッションを消す iwase
  いつ    : プロジェクトのセッションを最後の 1 つまで消したとき
  今は    : 見出しごと消え、戻るときは N の picker から探す
  これで  : 見出しが残り、数日後に j/k で辿り着ける
  その結果: 戻るプロジェクトを picker で探す操作が無くなる
  外れ判定: 台帳に残るプロジェクトが増えすぎて一覧が長くなり、利用者が
            まとめて消す操作を求める(= 残すことが価値ではなかった)
```

```
VH-002: 見出しから、そのプロジェクトで新セッションを始められる
  誰が    : 一覧を眺めている iwase
  いつ    : あるプロジェクトで新しい作業を始めたいとき
  今は    : 同じプロジェクトのセッションで f、無ければ N で picker
  これで  : 見出しにカーソルを合わせて n(または Enter)
  その結果: 新セッションの開始がプロジェクトの選択 1 回 + キー 1 回になる
  外れ判定: 見出しでの n がほとんど使われず、利用者が引き続き f / N を使う
```

```
VH-003: 見出しを選ぶと右 pane がそのプロジェクトの状態を見せる
  誰が    : 一覧を眺めている iwase
  いつ    : 見出しにカーソルを止めたとき
  今は    : 止まらない。右 pane は直前のセッションのまま
  これで  : ディレクトリ・git ブランチ・セッション数と「n で新規」のヒントが出る
  その結果: 選んでいるものと画面が一致し、空のプロジェクトでも次の一手が分かる
  外れ判定: カードの情報が見られず、利用者が「前のセッションを映し続けてほしい」と言う
```

## 価値の検証可能性

| 仮説 | 区分 | 受入での扱い |
|---|---|---|
| VH-001 | 機械判定可 | セッション 0 の登録済みディレクトリが `build_session_list` の行に見出しとして現れる |
| VH-002 | 機械判定可 | 見出し行で n → そのディレクトリの tmux セッションが生まれ、選択が新行に移る |
| VH-003 | 機械判定可 | 見出し選択時に view pane の画面にディレクトリ名とセッション数が描かれる |

「判断必要」に分類したものの分解を試みた記録:

- カードの「見やすさ」は判断必要だが、受入では「必要な 4 項目が描かれている」に
  分解する。配置の良し悪しは利用後に判断する。

## 非スコープ

**今回作らないもの。** 構築契約の I6 としてそのまま渡る。

- プロジェクトの並べ替え・固定・折りたたみ
- プロジェクト単位の一括操作(全セッション削除・全部再開)
- 台帳の手編集 UI(`tower project rm` と見出しでの D のみ)
- 見出しでの `i` / `r` / `t` / `w`(無視してヒントを 1 行出すに留める)
- GitHub など外部との連携
- 一覧の見出しへのセッション数表示(E-012): 分節の第3段で「行を見れば分かる」と判定(vf-articulate)。件数はカード(右 pane)にだけ出す
- 空プロジェクトの印(E-013): 同じく第3段で「行が無いことで分かる」と判定(vf-articulate)

## 判断

- [x] 作る / [ ] 作らない

理由: 3 つの作らない選択肢はいずれも利用者の意図(セッションは消す、
プロジェクトは残す)と噛み合わない。#67 の `tower open` / `project new` が
プロジェクト起点の操作を増やした今、台帳と見出し行は自然な続き。価値仮説は
3 つとも機械判定可。
