## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Navigator でキーを押してから画面が返るまでが遅く、操作感が悪い。特に N (新規ディレクトリ) と D (削除) で顕著だが、体感としては Navigator 全体の反応が鈍い。

原因は build_session_list の同期呼び出しにある。この関数は 1 セッションごとに状態判定・jsonl の grep・ディレクトリごとの live プロセス走査を行うため重く、コード自身がコメントで 'measured well into the seconds' と認めている (navigator-list.sh:311-321)。手元の実測でも 18 セッションで 3.67 秒かかった。

定期リフレッシュ (2秒ティック) はこの問題を既に回避しており、キャッシュを即座に読んでバックグラウンドで 1 本だけ再構築する設計になっている。ところが main_loop の n / f / N / D / r の各分岐 (navigator-list.sh:1041-1081) だけは build_session_list を直接呼んでおり、この回避策の外にいる。つまりキーを押すたびに、既に用意されている速い経路を使わず数秒の再構築を待たされる。

さらに各分岐は末尾で clear を呼ぶため、固まった後に画面が一度真っ白になってから描き直される。待ち時間と画面のちらつきが重なって、実際の遅延以上に壊れて見える。

セッション数に比例して悪化する性質なので、Tower を本来の用途 (多数のセッションを並行管理) で使うほど体感が悪くなる。

関連: 定期リフレッシュ側の非同期化は既に実装済みなので、同じ仕組みに乗せられるかがまず調べるべき点。ただし n/D の直後は『追加/削除した結果が即座にリストへ反映されてほしい』という要求があり、単純にキャッシュを読むだけでは古いリストが出る可能性がある。この要求と応答速度の両立が設計上の論点。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
2026-08-26: 稼働中の Navigator を実測したところ、キー操作時だけでなく **アイドル時も常時 CPU を食い続けている** ことが判明。こちらの方が深刻。

実測 (18 セッション):
- build_session_list 1 回 = 実時間 3.14 秒 / CPU 143% / **子プロセス生成 2,528 個**
- 1 セッションあたり約 140 プロセス。stat/grep/ps を外部コマンドで呼ぶため fork/exec が積み上がる

問題の構造: 再構築の投入間隔は 2 秒 (TICK_INTERVAL 0.25 x TICKS_PER_REFRESH 8) だが、1 回の所要が 3.14 秒でこれを上回る。_spawn_background_rebuild の多重起動ガード (navigator-list.sh:382-384) は正しく効いているので同時に 2 本は走らないが、前が終わった直後のティックが必ず次を投入するため **休止時間がゼロ**。CPU 143% の処理が途切れなく回り続ける。

実際に観測した稼働中プロセス: navigator-list.sh が 10 日間連続稼働で CPU 42% (親、スピナー再描画と再構築の起動分)、加えて子の再構築が常時 1 本。

セッション数に正比例するため、36 セッションなら 1 回 6 秒超。Tower を本来の用途で使うほど悪化する。

つまり修正の焦点は『キー操作時の同期呼び出しを非同期に寄せる』だけでは足りず、**build_session_list 自体のプロセス生成数を減らす**必要がある。あわせて、再構築の間隔を所要時間に応じて空ける (前回の所要を測って次まで休む) ことも要る。

2026-08-26 検証結果:

実データ・19セッションでの計測 (strace -f -e trace=execve, 決定論的):
- execve 1584 → 275 回 (82%削減)
- 内訳の変化: stat 1131→46, basename 128→52, grep 83→(get_session_title のパイプ除去)
- 実時間 7,208ms → 2,489ms (3回平均, 65%短縮)

アイドル時の再構築頻度 (0.4秒スタブで12秒間観測):
- 24回 → 3回 (REBUILD_MIN_GAP=5秒による休止導入)

テスト: 508 tests / 0 failures。main のベースラインと完全同一 (508/0) で退行なし。shellcheck クリーン。

AC#2 (古いキャッシュを表示しない): n/f/N/D/r の各分岐は従来どおり build_session_list を同期で呼んでおり、キャッシュ経路に変更なし。操作直後の反映は元の挙動を維持している。
AC#4 (セッション数に比例しない): 10/20/40 セッションで 1 件あたり execve 17→14→12 と逓減。線形以下。

AC#1 (待ちが体感で消えている) と AC#3 (ちらつきが出ない) は実 UI での目視確認が必要なため未チェック。#1 は実時間 65%短縮、#3 は clear 5箇所の除去という根拠はあるが、体感の確認は利用者に委ねる。

方針転換の記録: 当初 find_session_jsonl / get_session_cwd のメモ化を試みたが、計測で 60/60 の呼び出しがサブシェル内 (list_all_sessions はプロセス置換、_session_dir はコマンド置換) と判明。bash の連想配列は境界を越えられず効果ゼロだったため撤回した。真のボトルネックは get_session_activity の逐次 stat だった。

## Final Summary

<!-- SECTION:FINAL_SUMMARY:BEGIN -->
リスト再構築の外部コマンド起動を 1584→275 回 (82%減)、実時間 7.2→2.5 秒 (65%減) に短縮し、アイドル時の再構築を 12 秒あたり 24→3 回に抑えた。最大の原因は get_session_activity がファイルごとに stat を起動していたこと (1131/1584 回) で、これを 1 回のバッチ stat に統合。あわせて get_session_title の行ごとの printf|grep パイプ、ループ内の basename/dirname、_compose_row の sed 2 回、_content_width の tput 反復を bash 組み込みとパス単位のキャッシュに置換した。さらに再構築が終わった瞬間に次が始まる構造 (所要 > 間隔のため休止ゼロ) を、終了から 5 秒の間隔を要求する形に変更。検証は strace による execve 計数と bats 508 tests (0 failures, main と同一)。
