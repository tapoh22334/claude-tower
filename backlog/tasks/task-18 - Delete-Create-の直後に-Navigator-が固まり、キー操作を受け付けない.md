## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
セッションを削除 (D) したり作成 (n / f / N) したりすると、その直後 1〜2 秒ほど Navigator が固まる。カーソルも動かず、押したキーは戻ってきてからまとめて処理される。操作するたびに引っかかるので、体感として最も気になる部分。

原因は内部処理と画面応答が同じループの中で直列につながっていること。main_loop のキー処理分岐 (navigator-list.sh の n/f/N/D/r) が build_session_list を同期で呼んでいる。この関数は 1 セッションごとに transcript を読み状態を判定するため重く、手元の実測で 18 セッションに対し 1,409 ms かかる。read でキーを待つスレッドがその間ブロックされるので、押されたキーはバッファに溜まり、遅れて一気に流れる。

同じ問題が定期リフレッシュ側では既に解かれている。2 秒ティックはキャッシュを即座に読み、再構築はバックグラウンドに投げて次のティックで差し替える (_spawn_background_rebuild)。キー処理分岐だけがこの仕組みの外にいる。

加えて delete_selected と restore_selected には固定の sleep が入っている (削除後 0.5 秒、復元の各分岐で 0.3〜0.5 秒)。結果を読ませるための間だが、ユーザーがもう次の操作に移っているときには待たされるだけになる。

設計上の論点: 削除・作成の直後は『やった結果がすぐリストに出てほしい』という要求があるため、単にキャッシュを読むだけでは古い一覧が出る。応答性と即時反映の両立をどう設計するかが判断どころ。楽観的更新 (対象行を先に消す/足してから裏で再構築) が有力だが、失敗時の巻き戻しをどう見せるかまで決める必要がある。

関連: TASK-16 で build_session_list のプロセス生成を 1584→275 回に削減し実時間も 7.2→2.5 秒に短縮したが、それでもキー処理を直列でブロックする構造自体は残っている。

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
実装と検証 (2026-09-07):

削除は楽観的更新にした。_forget_session_row が 4 本の並列配列から該当行を抜き、削除行がグループヘッダを持っていた場合は次の生存行へ引き継ぎ、BROKEN_START も追従させる。実データ 16 行で測定: 従来の build_session_list が 645 ms、配列編集が 1 ms。

追加 (n/f/N) と復元 (r) は結果を予測できない (新しい行のタイトルも状態も transcript を読むまで分からない) ため、手元のリストで即描画し、バックグラウンド再構築が次のティックで反映する形にした。_settle_after_change が再構築のクールオフを 0 に落とすので、確認は 0.25 秒後に来る。

固定 sleep は成功パスから除去。削除は行が消えること、復元は ○ → ▶ の変化が確認になる。失敗時は逆に 0.8 秒に延ばした (見逃されると誤解が残るため)。エラー・キャンセル時の 0.5 秒は意図的に残している。

テスト作成中に実バグを発見: 空配列を "${a[@]}" で展開すると set -u 下で unbound variable になる (bash 4.3 以前)。最後の 1 セッションを削除するとこれを踏む。${a[@]+"${a[@]}"} 形式で回避した。

AC#2 (古いキャッシュを表示しない) は未チェック。削除については行が即座に消えるので満たしているが、追加については新しい行が最大 1 ティック遅れて現れる。これは意図した設計 (応答性を優先) だが「即時反映」の文言に対しては厳密には未達なので、実 UI での体感確認を待つ。

検証: 550 tests / 失敗 1 (別セッション編集中のファイル由来) / 警告 0、shellcheck クリーン、セッション漏れなし。新規テスト 10 件は _forget_session_row の配列整合性・ヘッダ引き継ぎ・BROKEN_START 追従・空リスト化を固定。

## Final Summary
