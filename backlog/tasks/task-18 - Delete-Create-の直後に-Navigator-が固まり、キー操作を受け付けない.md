## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
セッションを削除 (D) したり作成 (n / f / N) したりすると、その直後 1〜2 秒ほど Navigator が固まる。カーソルも動かず、押したキーは戻ってきてからまとめて処理される。操作するたびに引っかかるので、体感として最も気になる部分。

原因は内部処理と画面応答が同じループの中で直列につながっていること。main_loop のキー処理分岐 (navigator-list.sh の n/f/N/D/r) が build_session_list を同期で呼んでいる。この関数は 1 セッションごとに transcript を読み状態を判定するため重く、手元の実測で 18 セッションに対し 1,409 ms かかる。read でキーを待つスレッドがその間ブロックされるので、押されたキーはバッファに溜まり、遅れて一気に流れる。

同じ問題が定期リフレッシュ側では既に解かれている。2 秒ティックはキャッシュを即座に読み、再構築はバックグラウンドに投げて次のティックで差し替える (_spawn_background_rebuild)。キー処理分岐だけがこの仕組みの外にいる。

加えて delete_selected と restore_selected には固定の sleep が入っている (削除後 0.5 秒、復元の各分岐で 0.3〜0.5 秒)。結果を読ませるための間だが、ユーザーがもう次の操作に移っているときには待たされるだけになる。

設計上の論点: 削除・作成の直後は『やった結果がすぐリストに出てほしい』という要求があるため、単にキャッシュを読むだけでは古い一覧が出る。応答性と即時反映の両立をどう設計するかが判断どころ。楽観的更新 (対象行を先に消す/足してから裏で再構築) が有力だが、失敗時の巻き戻しをどう見せるかまで決める必要がある。

関連: TASK-16 で build_session_list のプロセス生成を 1584→275 回に削減し実時間も 7.2→2.5 秒に短縮したが、それでもキー処理を直列でブロックする構造自体は残っている。
